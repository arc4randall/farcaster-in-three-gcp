Farcaster in three commands, on Google Cloud

You end up with a Snapchain read node on a VM you pay for, and a small web client that reads from that node and posts through it. No Neynar key, no hosted API, nobody's node but yours.

Quickstart

Run these from Cloud Shell (gcloud is already logged in there) or any machine with gcloud set up and a billing-enabled project selected (gcloud config set project ID).

git clone https://github.com/arc4randall/farcaster-in-three-gcp && cd farcaster-in-three-gcp
  1. Provision compute (e2-standard-4, 2 TB pd-balanced disk, firewall for port 3382/udp): 
    ./provision.sh
  2. Start a Snapchain read node (Docker, image pinned to farcasterxyz/snapchain:0.14.3): 
    ./node.sh
    The node downloads a snapshot and then catches up. That takes hours; see sync.
  3. Run the client against your node. First run asks for your seed phrase and registers an app key; then open localhost:3000: 
    ./client.sh

To tear everything down: gcloud compute instances delete fc-node --zone us-central1-a. The disk is deleted with it.

Before you paste a seed phrase into anything, including this.
  • A seed phrase is total control of the account: it can transfer the FID, change the recovery address, and add or remove every key. Treat typing it as you would rm -rf /.
  • Use a test account. Make a throwaway FID for this tutorial rather than your main one.
  • Only paste a seed phrase into software you have read or whose developers you trust. Read client/setup.mjs (about 100 lines) before you run it.
  • Prefer delegated signer authorization when you can: an app that shows you a request to approve in a wallet or an existing client means the phrase never leaves where it already is. We use the phrase here only because the bounty asks for it.
  • What this client does with it: setup.mjs runs on your own VM and reads the phrase from your terminal (hidden input), so it travels only inside your encrypted SSH session. It derives the custody key in memory, signs two EIP-712 messages, and exits. The phrase is never written to disk, never sent to any other server, and never reaches the web UI. You can also run npm run setup in client/ on your laptop, with ports 3381 and 3383 tunnelled to the VM, then copy data/signer.json to the VM, if you'd rather it never leave your machine. Only the new app key is saved, in ~/fc-client-src/data/signer.json (mode 600) on your VM.

Before you start

  • A Google Cloud project with billing. The VM costs about $10/day (breakdown).
  • An existing Farcaster account (FID) that has storage, and its seed phrase. An account created in the Farcaster app has storage already. You do not need ETH: the app key is added gaslessly.
  • Patience for the first sync. The client cannot show a real feed until the node has caught up.

Concepts you need

FID

A Farcaster account is a number, the FID, issued by the IdRegistry contract on Optimism. Usernames like @alice are a separate layer pointing at an FID. Every message on the network is tagged with the FID that sent it. The client finds your FID by calling IdRegistry.idOf(custodyAddress) on Optimism.

Custody address

The Ethereum address that owns the FID. Your seed phrase derives it (path m/44'/60'/0'/0/0; set ACCOUNT_INDEX=1 if your wallet used the second address). The custody key doesn't sign casts. It authorizes other keys to sign for it, and it can transfer the FID. That is why you should keep it away from apps.

App keys (signers)

An app key is an Ed25519 keypair. The app holds the private half and signs every cast, like, and follow with it. Each key records which app asked for it: when the key is added, the requesting app's FID signs a SignedKeyRequest containing the key, and that requestFid is stored with the key. That is how this client can tell which app produced any cast on the network: look up the cast's signer among the author's keys and read its requestFid.

There are two ways to add a key:

  • Gasless KEY_ADD (FIP-272, live since engine V16, the default here). A Snapchain message carrying the app's SignedKeyRequest and the custody address's EIP-712 KeyAdd signature, wrapped in an envelope signed by the new key itself. No transaction. The key declares scopes (we ask for cast, reaction and link add/remove only) and a sliding TTL of up to 90 days that refreshes every time the key signs something. Each FID has a nonce counter; a KEY_ADD must use currentUserNonce + 1, which GET /v1/signersByFid reports.
  • Onchain KeyGateway.add on Optimism (0x00000000fC56947c7E7183f8Ca4B62398CaAdf0B). One transaction from the custody address, a few cents of ETH. Older, still valid, no scopes or expiry. Run ./client.sh --onchain if you want this path. Note the two flows sign different EIP-712 domains (getSignedKeyRequestMetadata vs getGaslessSignedKeyRequestMetadata); mixing them up is the most common error.

By default your own FID is the "app". To give this client a separate identity, register a second FID for it and set APP_SEED_PHRASE when running setup; every cast you post is then tagged with that app FID.

Snapchain messages

Everything you do is a protobuf Message: a MessageData body (type, FID, timestamp in seconds since 2021-01-01 UTC, network, and the body such as castAddBody), its BLAKE3 hash truncated to 20 bytes, an Ed25519 signature over the hash, and the signer's public key. Nodes accept a message only if the signer is a live key for that FID, the key's scope allows the type, and the FID has storage. Casts, likes and follows are sets with add/remove semantics: a later LINK_REMOVE beats an earlier LINK_ADD.

Read nodes vs validators

Every node runs the same binary. A handful of validators (seven on mainnet, listed in validators.toml) propose and vote on blocks. Anyone can run a read node: it fetches decided blocks from peers, checks their commit certificates against the validator set, applies them, and serves the HTTP API on 3381 and gRPC on 3383. It never votes. The data is split into shards: shard 0 orders the others, and shards 1 and 2 hold user messages, chosen by hashing the FID.

Storage rent

Messages occupy space on every node, so accounts rent storage from the StorageRegistry contract on Optimism. A unit lasts a year and caps each message type; when you exceed a cap, your oldest message of that type is pruned. Unit sizes changed over time, so check your own FID instead of trusting a table:

curl -s "localhost:3381/v1/storageLimitsByFid?fid=YOUR_FID" | jq

If an FID has no active storage, your node rejects its messages. That is the usual cause of a cast that "won't post" from a brand-new account.

How a write travels

The bounty text says read nodes don't accept writes. That was true of early Snapchain. Today POST /v1/submitMessage works on a read node, and this client sends every write there. Per the Snapchain docs:

  1. The client builds the message, hashes it, signs it with the app key, and POSTs the protobuf bytes to http://127.0.0.1:3381/v1/submitMessage on your node.
  2. Your node routes it to a shard (by FID; KEY_ADD goes to shard 0) and validates it against that shard's state: signature, key, scope, storage, duplicates.
  3. A read node has no mempool. It gossips the message on the mempool topic over UDP 3382 and keeps nothing.
  4. A validator picks it up from gossip into its mempool and includes it in a block it proposes.
  5. Your node syncs that block, and the message becomes readable.

So a 200 from submitMessage means "valid and relayed", not "in a block". If gossip drops it, it's gone. The client polls /v1/castById after posting and tells you if the cast never shows up, so you can resubmit. Submitting directly to a validator isn't an option for most people: validators don't publish an open API, and hosted endpoints such as Neynar's require a key or payment. Your own read node is the intended path.

You can set WRITE_URL to send writes to a different node's HTTP API; reads still come from yours.

Running the node

node.sh SSHes to the VM and runs remote/node-setup.sh, which does what the official snapchain.sh installer does, with two differences: it downloads docker-compose.mainnet.yml and validators.toml from the v0.14.3 tag rather than main, and it pins the image to farcasterxyz/snapchain:0.14.3 instead of :latest with pull_policy: always. To upgrade, change SNAPCHAIN_VERSION in config.env and re-run ./node.sh.

No API keys go in anywhere. The config is read_node = true, bootstrap peers are public IPs in the compose file, and the first boot pulls a snapshot from Farcaster's public R2 bucket.

gcloud compute ssh fc-node -- 'cd ~/snapchain && sudo docker compose logs -f --tail 20 snapchain'
gcloud compute ssh fc-node -- 'curl -s localhost:3381/v1/info | jq ".shardInfos[] | {shardId, maxHeight, blockDelay}"'

Phases: Downloading snapshots (chunk by chunk), decompression, then Processed decided block lines while it replays blocks since the snapshot. blockDelay is seconds behind; single digits on every shard means synced. mempoolSize: 4294967295 on a read node means "not reported", not an overflow.

Ports: 3382/udp is gossip and must be reachable. 3381 (HTTP) and 3383 (gRPC) are opened by provision.sh because the Snapchain docs ask for them. Run PRIVATE_API=1 ./provision.sh to leave them closed; the client works either way since it talks to 127.0.0.1.

The client

client.sh copies client/ to the VM, installs Node 22 and the pinned dependencies (@farcaster/hub-nodejs 0.17.0, viem, express), runs setup on first use, and starts the server on 127.0.0.1:3000. Your browser reaches it through the SSH tunnel (-L 3000:127.0.0.1:3000) that the same command opens. Nothing is exposed to the internet. On a phone, use the Cloud Shell web preview on port 3000.

What setup does

  1. Derives the custody account from the phrase and looks up its FID on Optimism.
  2. Generates a fresh Ed25519 key.
  3. Reads currentUserNonce from your node, signs the SignedKeyRequest (as the app) and KeyAdd (as custody), builds a KEY_ADD, and submits it to your node.
  4. Saves the app key and polls getSignersByFid until the key appears.

Troubleshooting

"owns no FID"

The phrase derived an address with no FID. Try ACCOUNT_INDEX=1.

KEY_ADD rejected: nonce

Another app added a key between our read and our submit. Run ./client.sh again; setup re-reads the nonce.

KEY_ADD rejected: invalid signature / domain

Onchain metadata was used for a gasless add or vice versa. Use makeKeyAddBody for gasless; it calls the gasless helper itself.

Cast accepted but never appears

Gossip dropped it. Post again. If it keeps happening, check that 3382/udp is open: gcloud compute firewall-rules list.

Empty feed

The node is still syncing (check blockDelay), or you follow nobody. Use "View" with a username to read any account.

Snapshot download restarts

Usually the disk filled up. df -h on the VM; the snapshot plus decompressed DB need well over 1 TB.

"Your node isn't answering on :3381"

The container isn't up yet or crashed: sudo docker compose ps and logs in ~/snapchain.
